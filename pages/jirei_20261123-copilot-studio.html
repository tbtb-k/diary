AI活用事例Copilot Studio2026年11月23日／IT・ソフトウェア（Microsoft サポート）・お客様からの技術サポート

自動で解決できるサポート案件が約10%から約35%に増えました。Microsoft サポートは、トピックごとのエージェントを1つにまとめました

Microsoft のサポート部門（Business Applications 担当）は、話題ごとにエージェントを作る方式では、扱う話題が数百に増えると作るのも保つのも追いつかない、という壁に当たっていました。

そこで、Copilot Studio（会話や作業の流れを組み立てて AI エージェントを作れるツール）で、数百の話題を1つで扱う「Dynamic Resolution Agent」を作り、別のエージェントが回答を確認してから送る形にしました。

Microsoft は、人の手を借りずに解決できる案件が「約10%から約35%近く」に増えたと公表しています。

01こんな場面、ありませんか

よくある質問ごとに自動応答を用意したら、質問の種類が増えるたびに、作る・つなぐ・試す・直す作業が雪だるま式に増えていく。いつの間にか、仕組みを保つこと自体が大きな仕事になっている。そんな経験はないでしょうか。

Microsoft のサポート部門も、技術的な話題ごとに専用の子エージェントを作り、親のエージェントから振り分けていました。この方式を製品ごとの数百の話題に広げるには、その数だけのエージェントと振り分け、テスト、保守が必要になります。担当者たちは、これを「拡張の壁」と呼んでいました。3つの話題のエージェントを作るのに5か月以上かかり、自動で解決できたのは案件の約10%でした。

02やってみたこと

チームは、Copilot Studio の新しい土台（出典では「Copilot harness」と呼ばれています）を使い、複数のエージェントを1つの「Dynamic Resolution Agent」に置きかえました。担当者は、エージェントの「頭脳」を仕組みや道具から切り離し、より身軽で広げやすい形にした、という意味のことを話しています。

このエージェントは、技術文書に加えて、サポートチームが書いた手順書（「スキル」と呼ばれます）を参照します。スキルはエージェントの外の Azure DevOps（開発チームがファイルや作業を管理する場所）に置かれ、案件ごとに必要なものだけを読み込みます。そのため、新しいスキルは、エージェントを作り直さずに追加と承認ができます。

  1. お客様が管理画面（Power Platform 管理センター）からサポートを依頼すると、Dynamics 365 Customer Service（お客様対応を管理するシステム）に案件ができます。
  2. 案件管理のエージェントが、お客様とのやり取りや催促、案件の終了を受け持ちます。
  3. Dynamic Resolution Agent が、お客様の状況と合う話題やスキルを選び、回答をつくります。
  4. 確認役の「Peer Review」エージェントが、Microsoft Learn など承認済みの情報にもとづいているか、正確で簡潔かを確かめます。
  5. 確認で通らなかったときや、エージェントが扱えないときは、メモを添えてサポートエンジニアに引き継ぎます。

03どう変わったか

これまで

話題ごとにエージェントを作る方式で、3つの話題のエージェントに5か月以上かかりました。自動で解決できたのは案件の約10%でした。

いま

最初のエージェントは数週間で完成し、別の製品向けは1週間後にできました。自動で解決できる案件は約35%近くに増えました。

いずれも Microsoft が公表した数字です。人が担当する案件でも、エージェントが集めた情報がエンジニアの対応を早めているとされています。一方で、対象期間や案件数、お客様の満足度、削減できた工数は公表されていません。

04明日から試すには

  1. いまある自動応答や FAQ を見直し、「話題ごとに作り分けているせいで手間が増えているところ」を探します。
  2. 担当者の頭の中にある対応手順を、話題ごとに短い手順書として書き出します。これがエージェントに読ませる「スキル」の元になります。
  3. Copilot Studio で、手順書と公式の文書を読ませたエージェントを1つ作り、回答は人が確認してから使う形で試します。

必要なもの：Copilot Studio の利用環境と、読ませてよい手順書や文書です。使える機能や料金、お客様対応のシステムとのつなぎ方は、会社のライセンスや管理者の設定で変わります。

05つまずきやすいところ

最初の作り方は「決めた通りに動く」ことに寄りすぎていました

出典では、初期のエージェントはとても決まりきった動きをするものだった、と担当者が振り返っています。話題ごとに分ける方式は分かりやすい反面、話題が増えると振り分けとテストと保守が重くなりました。新しい方式でも、回答を送る前に確認役のエージェントを通し、扱えないものは人に引き継ぐ、という歯止めを残しています。エージェントが自動で終えた案件も、Azure App Insights（動きを見守る監視の仕組み）で品質を確かめています。

社内で真似するときも、AI の回答をそのまま外に出さず、確認の段階を必ず入れましょう。AI はもっともらしい間違い（ハルシネーション）を答えることがあります。読ませる手順書に、お客様の情報や社外に出せない内容が混ざっていないかも、先に確かめてください。

06おわりに

この事例のポイントは、話題ごとに仕組みを作るのではなく、「1つのエージェントが、その場で必要な手順書だけを読む」形に変えたことです。手順書を足すだけで対応できる範囲が広がるので、仕組みを保つ手間をおさえながら育てていけます。

自分の職場に置き換えると、社内のヘルプデスクや総務の相談窓口でも、担当者ごとのノウハウを短い手順書にしておけば、同じ型で1つの相談エージェントにまとめられそうです。まずは、よく聞かれる3つの話題の手順書を書くところから始めてみてください。
