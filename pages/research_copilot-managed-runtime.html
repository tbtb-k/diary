ひとことで言うと

Copilot Managed Runtime は、Copilot などで作った社内向けアプリを、会社の Microsoft 365 の中で安全に動かすための「Microsoft が運営する置き場所」です。

アプリを作る道具ではなく、動かす場所です[26]。Copilot Cowork・Copilot Studio・Copilot Code・開発者向けツール・Lovable など、どれで作っても同じ置き場所に入り、会社アカウントでのサインイン、使ってよいデータの制限、共有のルールが最初から自動でかかります[1]。

管理者は Microsoft 365 管理センターで全アプリを一覧でき、問題があれば止められます[17]。2026年11月17日の Microsoft Ignite で一般提供（GA）が発表され、12月中旬にかけて各テナントへ順次届く予定です[24][27]。

5つの作り方と、管理者側の「最初の状態」

どれで作っても出来上がるものは同じ種類のアプリで、テナントの既定ルールを引き継ぎます[1]。違うのは「誰向けか」と「最初からオンかどうか」です。

Copilot Studio 作り手（メーカー） プレビュー体験をオンにして「アプリ」を選び、説明するかデータから始める。計画 → 下書き → 操作できるプレビューの順で進む オン pac admin update-tenant-settings でオフ、またはセキュリティグループに限定[13]
Copilot Code 業務担当〜開発者 クラウドのセッションで会話しながら作る（Cowork に近い体験）か、手元の PC で使う 支出ポリシー次第 Copilot Code 用の支出ポリシーに入っている人だけが作れる[13]

Copilot Studio のアプリ作成は「GitHub Copilot のしくみ（ハーネス）」で動いていると説明されています[22]。発表ブログでは GitHub Copilot・VS Code・Manus など他の開発ツールからの利用にも触れています[24]。

動くしくみ：アプリは「鍵」を持たない

安全性の芯はここです。アプリのコードはサンドボックス（隔離された箱）の中で動き、データにアクセスするときは必ずホストの「コネクタ代理」を通ります。認証の鍵（トークン）はホストが持ったままで、アプリには渡しません[4]。

よくある誤解：「アプリを共有したら、データも見えるようになる？」

なりません。共有で渡るのは「アプリを開く権利」だけで、データが見えるかどうかは、データ側（SharePoint など）で本人が権限を持っているかで決まります[19][27]。

開発の流れ：「保存」と「公開」が分かれている

開発者向けの CLI を使う場合の流れです。Git に送っただけでは本番は変わらず、公開は必ず明示的な1ステップになります。Cowork や Copilot Studio では、この流れを AI や画面が代わりに進めてくれます。

  1. 手元で作るms app dev手元で動かしながら編集。社内データ（SharePoint など）にもつながる[7]
  2. Git に送るgit push送っただけではビルドされない[7]
  3. プレビューms app play --mode previewここでビルド。失敗しても直前の成功版が表示され続ける[7]
  4. 本番に公開ms app deploy公開が終わるまで旧版が動き続ける。ビルド失敗なら公開は止まる[7][8]
  5. 共有ms app share最初は所有者しか開けないので、ここで相手を指定[7]
  6. 戻すms app deploy --commit <sha>問題があれば、以前のコミットをそのまま再公開[7]

すでに Power Platform を使っている会社は？

既存の環境ルーティング・環境グループ・ポリシーはそのまま尊重されます。そのため、実際に使えるコネクタは「高度なコネクタポリシー（ACP）があるか」と「ACP のみ」設定の組み合わせで決まります[14]。

 「ACP のみ」設定：オフ「ACP のみ」設定：オン

料金のしくみ：「作る」と「使う」で別々

課金は Copilot クレジットによる従量制が基本で、作るときと使う（動かす）ときで、かかるお金の出どころが違います[20]。

作る道具作るとき使う（動かす）とき
Copilot Cowork・Copilot CodeMicrosoft Copilot ライセンス＋Copilot クレジット（利用者単位の支出ポリシー）どの道具で作っても共通。利用者ごとに次のどちらかが必要：
① Power Apps Premium ライセンス（クレジットは消費しない・優先して使われる）
② Copilot Managed Runtime を含む支出ポリシー[20]
Copilot StudioCopilot Studio の環境課金

これだけでは動かせないもの：Microsoft 365 E3 / E5 などに付属する Power Apps の利用権、Microsoft 365 Copilot ライセンスだけ、Copilot Studio の環境課金[20][21]。クレジットがないと警告が出て、20回の操作か5分のどちらか早い方でブロックされます[5]。

公式のおすすめ設定（4ステップ）

  1. 管理センターの「Copilot > コスト管理」で従量課金をオンにする
  2. 全ユーザー向けの支出ポリシーを1つ作り、Copilot Managed Runtime を選んで、上限を1人月100クレジット（1ドル）にする
  3. よく使う人のグループ向けに、上限を高くしたポリシー（例：1,000クレジット＝10ドル）を追加する
  4. アラートを設定し、利用者からの「追加リクエスト」に対応する

ポリシーが重なった場合は「1人あたりの上限が一番高いもの」が適用され、上限に達しても別のポリシーには切り替わりません。上限は毎月1日にリセットされます。支払いは前払いの容量パック → 事前購入プラン（P3）→ 従量課金の順に使われます[20]。くわしくは次の「お金の出どころ」で整理しています。

お金の出どころ：「上限」と「支払い方法」は別もの

支出ポリシーは「使っていい上限」を決める設定で、お金を払う手段ではありません。公式にも「Spending policies are limits, not purchases（支出ポリシーは上限であって、購入ではない）」と書かれています[20]。支払い方法は、管理センターの「Copilot ＞ コスト管理 ＞ 開始」にある「Billing method」で別に選びます[20][29]。

  • P3 だけでは完結しません公式には「P3 と従量課金は別々の支払い方法ではなく、P3 は従量課金の上に乗る」と書かれています。P3 を使うときも、Azure サブスクリプションでの従量課金の設定が土台になります[29]。
  • 2027年1月1日から、P3 は EA か CSP パートナー経由でしか買えなくなります購入も更新も、エンタープライズ契約（EA）か販売パートナー（CSP）経由に限られます。オンラインでの購入は終わり、割引の扱いも変わると案内されています[33]。
  • 大企業向け：Azure の利用額の約束（MACC）に充てられますAzure の利用額を約束する契約（MACC）を結んでいる場合、従量課金と P3 の支払いはその消化に回ります[34]。
  • アプリを「使う」分には、定額の選択肢もありますPower Apps Premium ライセンスを持つ人は、Managed Runtime のアプリを使ってもクレジットを消費しません[20]。

買う窓口は3つ

窓口どんな会社向け？
Microsoft から直接（オンライン・MCA-E）管理センターや Azure を自分たちで操作できる会社
販売パートナー経由（CSP）国内のライセンス販売会社などから買う。手配・請求・サポートをパートナーがまとめて担当
エンタープライズ契約（EA）大企業向けの包括契約。通常はライセンス販売パートナーを通して結ぶ

どの窓口でどの商品（容量パック・P3・従量課金）を買えるかの公式の対応表は、ライセンスガイドの該当部分を本文で確認できなかったため未確認です[34]。

販売パートナー経由で買う主な理由

このページの整理家電を「メーカー直販」ではなく「量販店」で買うのに近い考え方です。

もう同じ窓口で契約している

Microsoft 365 や Azure をすでにそのパートナー経由で契約していれば、同じ契約に足すのが自然です。従量課金は Azure サブスクリプションに請求されるので、Azure をパートナー経由で契約していれば請求もそこから届きます。

P3 は今後パートナー経由が本命

2027年1月1日から、P3 の購入・更新は EA か CSP パートナー経由だけになります[33]。

日本の会社の購買ルールに合う

見積 → 稟議 → 発注 → 請求書払いの流れに乗せやすくなります。従量課金は月ごとに金額が変わる後払いなので、予算を取りにくいのが難点です。

相談できる

どの買い方がよいか、月いくらになるかの試算、管理センターの設定、更新期限の管理まで任せられます。クレジットは仕組みが複雑なので効果が大きい部分です。

値引きの相談ができる場合も

まとめ買いや他製品とのセットなど、パートナー独自の条件があるかどうかは会社によって違います。

財布は1つ、ポケットは別

Cowork・Copilot Code・Managed Runtime・Copilot Studio は、どれも同じ Copilot クレジットを使います。公式には「従量課金に対応した各サービスで使える共通の通貨」と書かれています[28]。違うのは、使っていい枠（ポケット）の決め方です。

ポケットが別だから起きること

  • Cowork 用のポリシーだけでは、アプリは使えませんアプリを作る分は作った人の Cowork の枠から、使う分は使った人の Managed Runtime の枠から引かれます。公式のトラブル例にも「Cowork だけを対象にしたポリシーでは、アプリの実行はまかなえない」とあります[20]。
  • 財布が尽きると、枠が残っていても全員止まります前払いの分を使い切り、従量課金もオフだと、アプリを使う人がまとめてブロックされる例が公式に載っています[20]。ほかのポケットの使いすぎで財布が尽きた場合も、理屈では同じことが起きます（「この順に止まる」とまでは書かれていません）。
  • Copilot Studio の管理は Microsoft 365 管理センターへ引っ越し中です希望した会社から移る形（オプトイン）です。Microsoft 365 側で環境を対象にしたポリシーを作ると、その環境では Power Platform 側の割り当てと課金プランが効かなくなり、ポリシーを外すと自動で戻ります。優先順位は「Microsoft 365 ＞ Power Platform」「環境・エージェント単位 ＞ 人単位」です[31]。

前払いのクレジットだけで運用する場合

従量課金を使わず、販売パートナーなどから買ったクレジットだけで回すやり方は、毎月の費用が読みやすいのが利点です。その代わり「尽きたら止まる」ので、Cowork やアプリを広げる前に次の点を押さえておきます。

  • 使い切ると、補充されるまで止まりますManaged Runtime のアプリは、前払いの分が尽きて従量課金もオフだと利用者がブロックされます[20]。Cowork などは、ポリシーの上限に達するとその月は使えなくなります[30]。
  • 環境への割り当てが多いと、Microsoft 365 側に回る分が減ります買ったクレジットをすべて Power Platform の環境に配りきっていると、Cowork やアプリに使える分はゼロになります[29]。「未割り当て」を残しておくのがポイントです。
  • 余っても繰り越せません容量パックは毎月補充される形です[32]。Copilot クレジットは毎月リセットされ、使い残しは翌月に繰り越されません（過去の調査メモ）。足りないと止まり、余るともったいないので、量の見極めが大事です。
  • 記載ゆれ容量パックが Cowork・アプリに使えるか、公式の書き方がそろっていませんManaged Runtime の課金ページは容量パックを支払い順の1番目に挙げ[20]、設定ページは「どちらの管理センターのサービスにも使える」としています[29]。一方、容量パックのページは「クレジットのポリシーは今のところ Copilot Chat だけ」と書いています[32]。容量パックだけで運用するときに Azure サブスクリプションが要るかも書かれていません。購入元に確認するのが確実です。

止めないための対策

  1. 従量課金を「保険」としてだけオンにする。前払いの分を使い切ったあとのはみ出し分にだけかかり、支出ポリシーの上限で使いすぎも防げます[20][29]
  2. アラートは財布全体の残高で見る。7〜8割を使った時点で気づけるようにします。パートナー経由の追加購入は手配に時間がかかるためです。消費状況は「Copilot ＞ コスト管理」で確認できます[20]
  3. 毎日アプリを使う人は Power Apps Premium にする。アプリの利用分のクレジットを消費しません[20]
  4. Copilot Studio の環境への割り当てを見直す。未割り当てを残すか、追加で買うかを決めます[29]
  5. P3 で買っている場合は、2027年1月からの変更を購入元に確認する[33]

導入前チェックリスト

GA 展開のお知らせ（メッセージセンター）で求められている準備と、公式の推奨手順をまとめました[27][4][20]。

  1. 従量課金をオンにし、全員向けの支出ポリシー（Copilot Managed Runtime を含む・1人月100クレジット）を作る。これがないと、Premium ライセンスのない人はアプリを使えません
  2. Cowork・Copilot Code で作る人を支出ポリシーに入れる。Copilot Studio はクレジットを作業環境に割り当てる
  3. 環境グループの既定ルール（コネクタ・CSP・共有）を確認し、組織全体リンクとゲスト共有の方針を決める
  4. プレビュー期間に作られたアプリを「すべてのアプリ」で棚卸しする
  5. 管理者ロール（閲覧専用も含む）を割り当て、監視のアラートを作る
  6. 作り手と利用者に周知する（「共有してもデータの権限は増えない」ことも伝える）

注意点：説明するときに外すと話がずれるところ

  • 展開は12月中旬まで続きますGA は「順次展開」です。テナントによって使える時期がずれるため、画面にまだ出ていなくても不思議ではありません[27]。
  • 「組織内のみ」のリンクに、ゲストが含まれることがありますゲスト共有をオンにしている場合、「組織内のみ」リンクはゲストも対象になると明記されています（現在はゲストが開けない既知の問題もあります）[4][14]。
  • 一度決めると変えられない設定がありますガバナンスの初期化後、「Everyone」の振り分けルールは変更も削除もできません。また、どのルールにも当てはまらない人はアプリを作れません[19]。
  • 既定ポリシーを編集すると、Microsoft の自動更新が止まりますコネクタや MCP サーバーの許可リストは Microsoft が更新していますが、管理者が編集した時点で以後の管理は自社の責任になります[14]。
  • Cowork で作ったものが全部 CMR アプリとは限りませんApp スキルで作ったアプリは CMR で動きますが、OneDrive に保存した HTML ページなどは CMR アプリではなく、管理センターの一覧にも出ません[19]。
  • Lovable 側でプロジェクトを消しても、アプリは残ります公開済みのアプリは管理センターでブロックか削除が必要です。Lovable Cloud のデータベースや関数は公開アプリに含まれません[11][12]。
  • 記載ゆれGA 直後で、ドキュメントの表記がそろっていませんGA の発表後も、一部のページ名に「(Preview)」が残っています（開発フロー、CLI リファレンス、セキュリティ管理）[7][9][15]。共有設定の場所も、ページによって「アプリ > 設定 > 環境グループ」と「設定 > アプリの設定」で書き方が違います[14][15]。実際の画面で確認してください。
  • 記載ゆれCowork の説明では「リンクを知っていれば誰でも使える」と読める書き方ですCowork のページは「リンクを持つ人は誰でもデータを含めてアプリを使える」と書いていますが[23]、CMR 側は「URL を知っているだけでは開けず、サインインと権限確認が必要」と説明しています[4]。組織全体リンクを指していると考えられますが、公式の裏付けは見つかっていません。
  • 未確認データの保存地域の約束は見つかりませんでした一覧には「ホストされている地域」の列があり、承認していない地域で動くアプリを見つけられるとされています[17]。ただし、どの地域で動くか、データ所在地をどう保証するかの記載は、今回読んだページにはありませんでした。
