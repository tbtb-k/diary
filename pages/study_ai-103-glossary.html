どの分野の問題文にも出てくる、AI の土台になる言葉です。ここがあいまいだと他の説明が頭に入りにくくなります。

モデルの種類

LLM（大規模言語モデル）★ 重要Large language model

大量の文章で学習した、文章を理解して書く AI モデルです。会話・要約・推論・コード生成など、幅広くこなします。

ツボ「難しい推論」「幅広い用途」なら LLM。安さ・速さが条件なら SLM と比べて選ぶ、という形で問われます。

[1]

SLM（小規模言語モデル）Small language model

中身の規模が小さく、軽くて安く速いモデルです。Microsoft の Phi シリーズなどがあります。

ツボ単純な分類や定型処理で、低コスト・低遅延が条件なら SLM が候補です。

[1][27]

マルチモーダルモデル★ 重要Multimodal model

文章だけでなく、画像・音声・動画もいっしょに入力して理解できるモデルです。

ツボ「写真について質問に答える」「図表を読む」なら、マルチモーダルモデルを選びます。

[1]

コードモデルCode model

プログラムの生成・説明・修正が得意なモデルです。出題範囲では「デプロイして使うモデル」の1つとして挙がっています。

[1]

推論モデルReasoning model

答える前に、内部で段階的に考えてから回答するモデルです。複雑な問題に強い代わりに、時間とトークンを多く使います。

[11]

入力と出力の単位

トークン★ 重要Token

モデルが文章を読み書きするときの細かい単位です。料金、1分あたりの上限（TPM）、一度に読める量は、すべてトークン数で決まります。

[4]

コンテキストウィンドウContext window

モデルが1回で読める量（トークン数）の上限です。会話の履歴や検索結果を詰め込みすぎると、ここを超えてしまいます。

[11]

プロンプトと指示（システムメッセージ）Prompt / instructions

プロンプトは AI への入力文です。指示（instructions、システムメッセージ）は、AI の役割・ルール・口調を最初に決めておく文章です。

[3]

埋め込み（ベクター）★ 重要Embedding

文章や画像の「意味」を数字の並びに変えたものです。意味が近いものほど数字も近くなるので、言い換えでも見つけられる「意味の検索」ができます。

[28][29]

品質と提供状態

グラウンディング★ 重要Grounding

AI の回答を、社内文書や検索結果などの信頼できる情報に「根拠づける」ことです。RAG は代表的なグラウンディングの方法です。

[1][5]

ハルシネーション（作り話）★ 重要Fabrication / hallucination

根拠がないのに、もっともらしい内容を AI が作ってしまうことです。出題範囲では fabrications（作り話）の検出として出てきます。

ツボ対策の答えは「グラウンディング」と「根拠性（Groundedness）の評価・検出」です。

[1][15]

GA とプレビューGeneral availability / Preview

GA は正式提供、プレビューはお試し提供（品質保証の SLA なし）です。試験は主に GA の機能から出ますが、よく使われるプレビュー機能が出ることもあります。

[1]

SDK と REST APISDK / REST API

どちらもプログラムからサービスを使う方法です。REST API は URL に直接リクエストを送る窓口、SDK はそれを Python などから簡単に呼べるようにした部品集です。

ツボ受験者像は「Python でアプリを開発した経験がある人」です。コードは読める程度に慣れておきます。

[1][2]

AIソリューションの計画・管理

Foundry の仕組み、モデルの置き方、権限とネットワーク、監視、責任あるAIの設定です。「この条件ならどの設定か」を問う問題が多い分野です。

Foundry の基本

Microsoft Foundry★ 重要旧 Azure AI Foundry／Azure AI Studio

エージェント・モデル・ツールを1か所にまとめて、作る・試す・公開する・見張るための Azure の基盤です。権限・ネットワーク・ポリシーも1つの単位で管理できます。

ツボこの試験の主役です。教材や問題文の「Azure AI Foundry」は同じものを指します。

[2]

Foundry リソースFoundry resource

Azure 上に作る「親の箱」です。管理・セキュリティ・監視の境界になり、この中にプロジェクトを作ります。以前の「Hub＋Azure OpenAI＋AI Services」の組み合わせが1つにまとまりました。

[2][12]

Foundry プロジェクト★ 重要Foundry project

リソースの中に作る、チームごとの作業部屋です。エージェント・データ・権限をプロジェクト単位で分けます。アプリは「プロジェクトのエンドポイント」1つに接続して使います。

ツボ出題範囲に「アプリを Foundry プロジェクトに接続する設定」がはっきり書かれています。

[1][2][12]

Foundry ポータルai.azure.com

ブラウザで使う Foundry の画面です。プレイグラウンド（お試し画面）で、モデルやエージェントをコードなしで試せます。旧画面は Foundry (classic) と呼ばれます。

[2]

Foundry Tools★ 重要旧 Azure AI Services

Speech（音声）、Translator（翻訳）、Language（文章分析）、Document Intelligence、Content Understanding、Vision など、用途別の AI 部品の総称です。

[2]

Foundry Models（モデルカタログ）Model catalog

Microsoft、OpenAI、Anthropic、Meta などの1万を超えるモデルから選べる一覧です。

[2]

モデルベンチマークModel benchmarks

公開データや自社のデータで、モデルの品質や性能を比べる機能です。どのモデルを使うかを決める判断材料になります。

[14]

モデルルーターModel router

1つのデプロイの裏側で、質問ごとに最適なモデルを自動で選ぶ仕組みです。Balanced（既定）、Quality（品質優先）、Cost（コスト優先）の3つのモードがあります。

ツボ「簡単な質問は安いモデル、難しい質問は賢いモデルに自動で振り分けたい」ならこれです。

[11]

Azure Developer CLI（azd）azd

コマンドで、AI アプリやホステッドエージェントのひな形作成・テスト・デプロイを行うツールです。

[2]

デプロイとキャパシティ

デプロイDeployment

モデルを、アプリから呼び出せる状態に設置することです。アプリはデプロイ名を指定して呼びます。一部のモデルは、デプロイせず名前だけで呼べる「インスタントアクセス（プレビュー）」も使えます。

[4]

デプロイの種類★ 重要Deployment types

「データをどこで処理するか（Global／Data Zone／地域）」と「どう払うか（従量課金／予約／バッチ）」の組み合わせです。

ツボ迷ったら Global Standard から始める、というのが公式の推奨です。理由（データの所在・予約・一括処理）があるときだけ他を選びます。

[4]

Global StandardGlobalStandard

既定のおすすめです。新しいモデルが最初に出て、価格が一番安く、使える地域も最多です。代わりに、どの地域で処理されるかは選べません。

[4]

Data ZoneDataZoneStandard など

処理を US・EU・APAC（アジア太平洋）の範囲内に限定する種類です。「EU の外で処理してはいけない」などの要件があるときに選びます。

[4]

プロビジョンド（PTU）★ 重要Provisioned throughput unit

処理能力を PTU という単位で予約する方式です。遅延のばらつきが小さく、毎日安定して大量に使う本番向けです。

ツボ「予測できる大量の負荷」「遅延を安定させたい」→ PTU。

[4]

バッチGlobal Batch／Data Zone Batch

大量のリクエストを1ファイルにまとめて送り、あとで結果を受け取る方式です。24時間以内の完了が目標で、Global Standard より50%安くなります。

ツボ「急がない大量処理を安く」→ バッチ。リアルタイム応答には使えません。

[4]

Developer デプロイDeveloperTier

ファインチューニングしたモデルを試すためだけの種類です。24時間で自動的に削除され、SLA もありません。

[4]

サーバーレス API とマネージドコンピューティングServerless API / Managed compute

サーバーレスは、Microsoft が運用するモデルを従量課金で使う方式です。マネージドコンピューティングは、オープンソースや独自のモデルを専用の計算資源に載せる方式です。上の「デプロイの種類」はサーバーレス側の話です。

[4]

クォータ（TPM／RPM）★ 重要Quota

1分あたりに使えるトークン数（TPM）とリクエスト数（RPM）の上限です。デプロイや地域ごとに割り当てて使います。

[4][11]

レート制限と 429 エラーRate limit

上限を超えたときに返る「混みすぎ」のエラーです。時間をあけての再試行、クォータの増加申請、別の地域の利用、PTU への切り替えなどで対処します。

[4][22]

コストの管理Cost footprint

生成AIの費用は、おもに「トークン量 × 単価」で決まります。小さいモデル、バッチ、モデルルーター、プロンプトキャッシュの活用で下げられます。

[1][4][11]

CI/CD★ 重要Continuous integration / deployment

コードの変更を自動でテストし、本番環境まで自動で届ける仕組みです（GitHub Actions、Azure DevOps など）。プロンプトエージェントも、SDK や REST で定義すればパイプラインに組み込めます。

ツボ評価を「品質の関門（品質ゲート）」としてパイプラインに入れる考え方も押さえます。

[1][3][14]

セキュリティ

Microsoft Entra ID旧 Azure Active Directory

Microsoft の ID とアクセス管理の仕組みです。人・アプリ・エージェントが「誰なのか」を証明します。

[12]

キーレス認証★ 重要Keyless credentials

API キー（合鍵のような文字列）を使わず、Entra ID で認証することです。キーは全権を持ち、役割による制限が効きません。

ツボ「RBAC で細かく権限を絞りたい」「キーの漏えいを防ぎたい」→ キーレス（Entra ID）。

[12]

マネージド ID★ 重要Managed identity

Azure がアプリやプロジェクトに自動で発行する「社員証」です。パスワードやキーを管理せずに、ほかの Azure サービスへ安全にアクセスできます。

ツボ例：プロジェクトのマネージド ID に、ストレージの「Storage Blob Data Reader」ロールを付けて資料を読ませる。

[12]

RBAC（ロールベースのアクセス制御）★ 重要Role-based access control

「誰に」「どの範囲（スコープ）で」「どの役割（ロール）を」与えるかで権限を決める仕組みです。必要最小限の権限だけを与えるのが基本です。

[12]

Foundry の組み込みロール★ 重要Foundry User ほか

目安は、Foundry User＝作って試す開発者、Foundry Project Manager＝プロジェクトの管理とエージェントの公開、Foundry Account Owner＝リソースとモデルの管理、Foundry Owner＝すべて、Foundry Agent Consumer＝エージェントを呼ぶだけ、です。

ツボ旧名は Azure AI User、Azure AI Project Manager など。教材によって旧名のことがあります。

[12]

プライベートネットワーク★ 重要Private networking / VNet

インターネットに出さず、会社の仮想ネットワーク（VNet）の中だけで通信させる構成です。プライベートエンドポイントで、Azure のサービスを社内側につなぎます。

[1][3]

エージェント IDAgent identity

エージェントごとに専用の Entra ID を持たせ、アクセスできる範囲を個別に絞る仕組みです。利用者本人の権限で動かす OBO（On-Behalf-Of）にも対応します。

[3]

Azure PolicyAzure Policy

組織のルールを強制する仕組みです。例：特定のデプロイの種類を使えなくする、使ってよいモデルを制限する。

[4][11]

監視とガバナンス

Foundry Control PlaneFoundry Control Plane

複数のプロジェクトにまたがるエージェント・モデル・ツールを一覧し、品質・コンプライアンス・セキュリティ・コスト・トークン使用量をまとめて管理する画面です（ポータルの Operate）。

[13]

AI ゲートウェイAzure API Management

モデルの手前に置く「関所」です。トークン上限の強制など、高度なガバナンス機能を使うときに必要です。

[13]

Application Insights／Azure MonitorApplication Insights

トレースや数値（トークン量・遅延・エラー率）を保存し、ダッシュボードやアラートで確認する Azure の監視サービスです。

[14]

ドリフト★ 重要Drift

時間がたつにつれてデータや使われ方が変わり、AI の品質がじわじわ落ちていくことです。テストデータで定期的に評価して見つけます。

[1][14]

取り込みの品質とインデックスの健全性Ingestion quality / index health

RAG の検索側の監視です。取り込みの失敗や古いデータがないか、検索の当たり具合（関連性）が落ちていないかを見ます。

[1]

責任あるAI

責任あるAIResponsible AI

AI を安全・公平に使うための考え方と仕組みです。Microsoft は、公平性、信頼性と安全性、プライバシーとセキュリティ、包括性、透明性、説明責任の6原則を掲げています。

ツボ出題範囲では、フィルター・評価・監査・承認フローといった「具体的な設定」として出てきます。

[1]

ガードレールとコントロール★ 重要Guardrails and controls

ガードレールは安全対策の設定のまとまりで、中身は複数のコントロールです。1つのコントロールは「どのリスクを」「どこで（介入ポイント）」「どうするか（注釈／ブロック）」を決めます。モデルの既定は Microsoft.DefaultV2 です。

ツボエージェントに割り当てたガードレールは、モデル側の設定を完全に上書きします。割り当てがなければ、モデルのものを引き継ぎます。

[16]

介入ポイント★ 重要Intervention points

チェックをかける場所のことで、ユーザー入力・ツール呼び出し・ツールの応答・最終出力の4つです。ツールの2つはエージェントだけ（プレビュー）です。

[16]

有害カテゴリとブロックレベルHate／Sexual／Violence／Self-harm

ヘイト・性的・暴力・自傷の4つを重大度で判定します。ブロックレベル Low は「重大度が高いものだけ止める（ゆるい）」、High は「低〜高まで全部止める（厳しい）」です。

ツボ名前と厳しさが逆に感じやすいので注意。正当な文章まで止まるときは、レベルを下げるか「注釈のみ」にします。

[16]

Azure AI Content SafetyContent Safety

文章や画像の有害な内容を見つけるサービスです。ガードレールの判定もこの分類モデルを使っています。単体の API としても使えます。

[16][18]

Prompt Shields★ 重要旧 Jailbreak risk detection

AI を乗っ取ろうとする入力を見つける盾です。利用者が直接仕掛ける「ユーザープロンプト攻撃」と、資料の中に命令を隠す「ドキュメント攻撃」の2種類を検出します。

ツボユーザー側は既定でオン、ドキュメント側は既定でオフです。外部の資料を読ませるなら自分で有効にします。

[17]

間接プロンプトインジェクション（XPIA）★ 重要Cross-prompt injection attack

文書・メール・Web ページ・画像の文字などに「指示を無視して〜せよ」と隠しておき、それを読んだ AI を操る攻撃です。

[1][17]

スポットライティングSpotlighting（プレビュー）

外部の文書を base64 という形式に変換して「信用度の低いデータ」だと分からせ、中の命令に従いにくくする追加の防御です。トークンが増え、Chat Completions API でのみ使えます。

[17]

保護された素材の検出Protected material

歌詞や記事など既知の文章や、既存のコードと一致する出力を見つけます。著作権まわりの対策です。

[16][18]

根拠性の検出Groundedness detection（プレビュー）

回答が渡した資料に基づいているかを、その場でチェックする安全機能です。モデルには使えますが、エージェントにはまだ使えません。

[16][18]

タスク準拠Task adherence

エージェントのツールの使い方が、依頼の内容からずれていないか、早すぎないかを見つけます。

[16][18]

評価とエバリュエーター★ 重要Evaluation / evaluators

AI の回答の品質・安全性を点数で測ることです。エバリュエーターは採点方法のことで、判定役の AI が採点するものと、計算で出すものがあります。

ツボモデル選び → 公開前のテスト → 公開後の継続評価、の3段階で使います。

[14][15]

安全性の評価Risk and safety evaluators

ヘイト・暴力などの有害さ、保護された素材、間接攻撃（XPIA）への弱さ、生成したコードの脆弱性、機密データの漏えいなどを採点します。

[15]

AI レッドチーミングエージェントAI Red Teaming Agent

わざと攻撃を仕掛けて弱点を探す自動テストです（Microsoft の PyRIT を使用）。人によるレビューと組み合わせて使います。

[14]

監査と来歴メタデータ★ 重要Auditing / provenance metadata

「誰が・いつ・何を実行／承認したか」「この回答はどの資料から来たか」の記録を残すことです。トレースのログ、出典の情報、承認のログで実現します。

[1][7]

承認フロー（ヒューマン・イン・ザ・ループ）★ 重要Approval workflow / human-in-the-loop

重要な操作の前で止まり、人の承認を待つ仕組みです。例：MCP ツールの require_approval を always にすると、ツールを使う前に毎回承認を求めます。

[7][9]

ツールのアクセス制御allowed_tools

エージェントが使ってよいツールを、許可リストで絞ることです。データを書き換えるツールほど、承認とセットにします。

[7]

監督モードと制約Oversight modes / constraints

出題範囲の言葉で、エージェントにどこまで任せ、どこで人が見張るかを決めることを指します。使えるツールの制限や承認の有無で調整します。

[1]

生成AIアプリの基本

RAG（検索拡張生成）★ 重要Retrieval-augmented generation

質問に関係する資料を先に検索して、その内容をモデルにいっしょに渡して答えさせる方法です。社内データや最新情報に答えられ、出典も示せます。

[1][5]

チャンク分割Chunking

長い文書を、検索しやすい大きさの小片（チャンク）に切り分けることです。

[5][28]

プロンプトエンジニアリング★ 重要Prompt engineering

指示の書き方を工夫して、出力を良くすることです。役割・手順・出力の形・例を具体的に書くのが基本です。

[1]

フューショット（例示）Few-shot

指示の中に「入力と正しい出力の例」をいくつか入れて、形式や判断の基準をまねさせる方法です。

[1]

モデルのパラメーター★ 重要temperature／top_p／max tokens

temperature を下げると回答が安定し、上げると多様になります。top_p も多様さの調整です。max tokens は出力の長さの上限です。

ツボ「毎回ぶれない、事実ベースの答えがほしい」→ temperature を下げます。

[1]

構造化出力（JSON スキーマ）★ 重要Structured outputs

出力を、決めておいた JSON の形に合わせさせる機能です。後ろのプログラムがそのまま読めるので、データ抽出やシステム連携に向きます。

[1][9]

ファインチューニング★ 重要Fine-tuning

自分のデータでモデルを追加で学習させることです。口調・出力の形式・特定の作業のやり方を覚えさせるのに向きます。

ツボ新しい知識を足したいだけなら、RAG のほうが手軽で更新もしやすい、が定番の判断です。

[1][4]

Responses API旧 Assistants API

Foundry でモデルやツールを呼ぶための標準の API です（Agents v2）。会話の状態やツールの呼び出しもまとめて扱えます。

[2][3]

Foundry SDKazure-ai-projects

プロジェクトのエンドポイント1つに接続して、モデル・エージェント・評価などを使うための統一の部品集です。OpenAI 互換のクライアントと組み合わせて使います。

[2]

プロンプトキャッシュPrompt caching

同じ書き出しのプロンプトを再利用して、コストと待ち時間を減らす仕組みです。

[11]

エージェントAgent

指示・モデル・ツールを設定するだけで作るエージェントです。コードやサーバーの管理はいらず、Foundry が実行します。

[3]

ホステッドエージェント★ 重要Hosted agent

自分で書いたコード（Agent Framework、LangGraph など）をコンテナにして、Foundry 上で動かすエージェントです。一番自由度が高く、独自の段取り（オーケストレーション）も組めます。

音声プロンプトエージェントVoice-based prompt agent（プレビュー）

Voice Live を通じて、リアルタイムに声で会話できる管理型のエージェントです。電話（Teams Phone、Twilio）にもつなげられます。

[3]

エフェメラルエージェントEphemeral agent

Foundry にエージェントを保存せず、アプリのコードの中で指示やツールを組み立てて Responses API を直接呼ぶ使い方です。

[3]

Conversation／Item／Response／Agent version旧 Thread／Message／Run／Assistant

会話（Conversation）は一連のやり取り、アイテム（Item）はその中の1つ1つのメッセージなど、レスポンス（Response）は1回の応答、エージェントバージョンは保存するたびに残る版です。

ツボ古い教材は Thread／Run という言葉で説明しています。対応関係を覚えておけば読み替えられます。

[2]

役割・目標・会話の追跡Roles, goals, conversation tracking

エージェントを設計するときに最初に決めることです。何者で（役割）、何を達成し（目標）、会話の履歴をどう持ち回るか（追跡の方法）を、指示や設定に落とし込みます。

[1]

公開とバージョン管理Publishing / versioning

保存するたびにバージョンが残り、公開すると安定したエンドポイントができます。Microsoft Teams や Microsoft 365 Copilot へ配布できます。

[3]

エージェントオプティマイザーAgent optimizer（プレビュー）

エージェントの動きを評価して、より良い指示・ツールの説明・モデルの選択を自動で提案する機能です。

[3]

ツールと記憶

ツールTools

エージェントが外の世界に働きかける手段です。組み込み（Web 検索、ファイル検索、コードインタープリター、Azure AI Search など）と、自作（関数、OpenAPI、MCP）があります。

[3][6]

関数呼び出し★ 重要Function calling

モデルが「この関数をこの引数で呼んで」と返し、実際の実行はアプリ側で行う仕組みです。社内システムの処理を AI から使わせたいときに使います。

[6]

ツールスキーマ★ 重要Tool schema

ツールの名前・説明・引数の形を JSON で書いた「取扱説明書」です。モデルはこれを読んでツールを選ぶので、説明文の分かりやすさが精度を左右します。

[1][6]

OpenAPI ツールOpenAPI

Web API の設計書（OpenAPI 仕様）を渡すだけで、その API をツールとして呼べるようにする仕組みです。

[6]

MCP★ 重要Model Context Protocol

AI とツールをつなぐための共通規格です。MCP サーバーとして公開されたツールなら、対応するエージェントから同じ方法で使えます。

[6][7]

ツールボックスToolbox

よく使うツールを1つの箱にまとめ、1つの MCP 互換の窓口から複数のエージェントに配る仕組みです。認証・ガードレール・バージョンをまとめて管理できます。

[6]

ツール検索とスキルTool search / Skills（プレビュー）

ツール検索は、大量のツールから必要なものだけをその場で探す仕組みです。スキルは、複数の手順を「やり方」としてまとめて再利用する部品です。

[6]

コードインタープリターCode interpreter

エージェントが安全な隔離環境（サンドボックス）で Python を動かし、計算・グラフ作成・ファイル処理をするツールです。

[6]

ファイル検索File search

利用者がその場でアップロードした文書を検索して答えるためのツールです。

[6][8]

Web 検索Web search／Grounding with Bing

Web の最新情報を調べて答えるためのツールです。

[6]

ブラウザー自動化と Computer useBrowser automation / computer use

Web ページや画面を見て、クリックや入力を代わりに行うツールです。

[6]

会話の履歴（短期の記憶）Short-term memory

いま進んでいる会話の流れのことです。会話（Conversation）の中に保持されます。

[8]

メモリ（長期の記憶）★ 重要Memory（プレビュー）

会話をまたいで、利用者の好みや過去の話題を覚えておく仕組みです。ユーザープロフィール、チャットの要約、手順（procedural）の3種類があります。

[8]

複数エージェントとワークフロー

マルチエージェント★ 重要Multi-agent

役割の違う複数のエージェントが、分担・連携して1つの仕事を進める構成です。

[1][10]

オーケストレーション★ 重要Orchestration

複数のエージェントや処理の動かし方の段取りです。順番に渡す「順次（sequential）」、状況に応じて話し手を替える「グループチャット」、人の確認をはさむ「ヒューマン・イン・ザ・ループ」などのパターンがあります。

[9][10]

A2A（Agent-to-Agent）★ 重要A2A protocol

別々に作られたエージェント同士が、仕事を頼み合うための共通規格です。Foundry では v1.0 が GA です。

[3][6]

Microsoft Agent Framework★ 重要Semantic Kernel と AutoGen の後継

エージェントとワークフローをコードで作るための、Microsoft のオープンソースの開発キットです（Python、.NET など）。

ツボ「関数で書ける処理なら、AI エージェントではなく関数で」という考え方が公式に書かれています。

[10]

ワークフロー★ 重要Workflow

手順・分岐・人の承認をあらかじめ決めておき、エージェントや処理をその通りに動かす仕組みです。

ツボFoundry のビジュアルなワークフロー（プレビュー）は 2026年12月1日に廃止予定で、Agent Framework への移行が推奨されています。

[9][10]

自律型と半自律型Autonomous / semiautonomous

人の確認なしで最後まで動く（自律型）か、要所で人が承認する（半自律型）かの違いです。お金やデータの変更など、影響の大きい操作には承認を入れます。

[1][7]

[15]

関連性（Relevance）Relevance evaluator

回答が、質問にきちんと答えているかを採点します。

[15]

一貫性と流暢さCoherence / Fluency

話の筋が通っているか（一貫性）、言葉として自然か（流暢さ）を採点します。

[15]

検索の評価Retrieval / Document Retrieval

RAG で、必要な資料をうまく取ってこられたかを採点します。

[15]

エージェントの評価Intent Resolution／Task Adherence／Tool Call Accuracy

依頼の意図を正しくつかんだか、指示どおりに進めたか、正しいツールを正しい引数で呼んだか、などを採点します。

[15]

類似度の指標F1／BLEU／ROUGE

正解の文章と、どれだけ言葉が重なるかで測る指標です。翻訳や要約の評価によく使われます。

[15]

エラー分析（クラスター分析）Error analysis / cluster analysis

失敗した回答をパターンごとにまとめて、原因を見つけやすくする機能です。

[14]

思考の連鎖Chain-of-thought

答えにたどり着くまでの考えを、段階的に書かせる手法です。出題範囲では、その考え方が妥当かを評価する話として出てきます。

[1]

リフレクションと自己批評ループModel reflection / self-critique loops

AI に一度答えさせたあと、自分で見直して採点・修正させることを繰り返す手法です。品質は上がりますが、時間とトークンは増えます。

[1]

可観測性（オブザーバビリティ）Observability

評価・監視・トレースによって、AI の中で何が起きているかと、その品質を見えるようにすることです。

[14]

トレース★ 重要Tracing

1回の処理の中で、どのモデル呼び出し・ツール呼び出し・判断が、どの順番で何秒かかったかを記録したものです。OpenTelemetry という標準の形式で、Application Insights に保存します。

ツボ出題範囲の「トークン分析」「安全シグナル」「遅延の内訳」は、トレースと監視で見ます。

[1][14]

LLM とルールエンジンの組み合わせHybrid LLM and rules engines

決まったルールで処理できる部分は普通のプログラムに、あいまいな判断だけを LLM に任せる構成です。

[1][10]

検索の土台

Azure AI Search★ 重要旧 Azure Cognitive Search

データを取り込んで索引を作り、キーワード・ベクター・ハイブリッドで検索できるサービスです。Foundry IQ の土台でもあります。

取り込みの時に、文書の分割（Text Split スキル）からベクター化（埋め込みスキル）までを自動で行う仕組みです。

検索の種類

全文検索（キーワード検索）Full-text search / BM25

言葉の一致で探す検索です。型番・人名・日付など、ぴったり一致させたいものに強いです。

[29]

ベクター検索★ 重要Vector search

埋め込み（意味を表す数字）の近さで探す検索です。言い換えや表記のゆれにも強いです。

[29]

ハイブリッド検索★ 重要Hybrid search

キーワード検索とベクター検索を同時に行い、結果を1つにまとめる検索です。まとめ方には RRF を使います。

[29]

RRFReciprocal Rank Fusion

複数の検索結果を、それぞれの「順位」をもとに混ぜ合わせる方法です。

[29]

セマンティックランカー★ 重要Semantic ranker

最初の検索結果の上位50件を、言語を理解するモデルで並べ替える「2段目の採点」です。要点（キャプション）や回答の抜き出しもします。新しい文章は作りません。

[30]

エージェント型検索★ 重要Agentic retrieval

LLM が複雑な質問を小さな質問に分け、並行して検索し、結果を並べ替えてまとめる検索の仕組みです。Foundry IQ の中心です。

[5]

知識をエージェントにつなぐ

Foundry IQ★ 重要Foundry IQ

社内のさまざまなデータをまとめた「ナレッジベース」を作り、エージェントに、権限を守った根拠つきの回答材料を渡す知識の層です。

[5]

ナレッジベースとナレッジソースKnowledge base / knowledge sources

ナレッジソースはつなぐデータ（Blob ストレージ、SharePoint、OneLake、Web など）、ナレッジベースはそれらをまとめて検索する窓口です。複数のエージェントで共有できます。

[5]

権限に応じた検索結果ACL / Purview sensitivity labels

質問した人が見てよい文書だけを返す仕組みです。アクセス権の設定や Microsoft Purview の秘密度ラベルを、検索の時点で反映します。

[5]

Azure AI Search ツールAzure AI Search tool

エージェントから、既存の検索インデックスを直接検索するためのツールです。

[6]

RAG の取り込みの流れ★ 重要RAG ingestion flow

文書を読み取る（OCR・レイアウト分析）→ 分割する → ベクター化する → インデックスに入れる → エージェントのツールやナレッジにつなぐ、の順番です。

[1][5][28]

文書から情報を取り出す

OCR（光学文字認識）★ 重要Optical character recognition

画像やスキャンした PDF の文字を読み取って、テキストにすることです。

[21][28]

レイアウト分析★ 重要Layout analysis

段落・見出し・表・チェックボックスなど、文書の構造を読み取ることです。表を崩さずに取り込めるので、RAG の質が上がります。

[21][23]

フィールド抽出★ 重要Field extraction

請求書の「合計金額」のように、あらかじめ決めた項目（スキーマ）の値を取り出すことです。Content Understanding では「抽出（extract）」「分類（classify）」「生成（generate）」の3つの方法があります。

[21]

Content Understanding★ 重要Azure Content Understanding in Foundry Tools

文書・画像・音声・動画を生成AIで処理し、Markdown や決まった形の JSON で出力するサービスです。値ごとに確からしさ（信頼度）と、元のどこから取ったか（根拠の位置）も返します。

[21]

アナライザー★ 重要Analyzer（prebuilt / custom）

Content Understanding で「何を・どう処理して・どんな形で出すか」をまとめた設定です。請求書・契約書・通話分析などの既製アナライザーと、自分で作るカスタムアナライザーがあります。

[21]

Markdown 出力Markdown output

見出しや表を保ったまま、きれいなテキストにする出力形式です。RAG やエージェントが読みやすくなります。

[21]

信頼度スコアと根拠の位置Confidence scores / grounding

取り出した値がどれくらい確かか（0〜1）と、元の文書のどこから取ったかの情報です。人が確認する手間を減らす判断材料になります。

[21]

分類と分割Classification / segmentation

1つのファイルに混ざった複数の書類を種類ごとに分け、それぞれに合うアナライザーへ回すことです。

[21]

Document Intelligence旧 Form Recognizer

決まった形式の書類から、確実に情報を抜き出す文書処理サービスです。Read（文字）、Layout（構造）、事前構築モデル（請求書・領収書など）、カスタムモデル（テンプレート・ニューラル・合成・分類）があります。

[23]

マルチモーダルな抽出パイプラインOCR + layout + field extraction

OCR・レイアウト分析・フィールド抽出を組み合わせて、文書や画像から整理された情報を作る一連の処理です。

[1][21]

プロンプトエージェントvsホステッドエージェント

プロンプト
指示・モデル・ツールを設定するだけ。コードもサーバー管理も不要。
ホステッド
自分のコードをコンテナで動かす。独自の処理の流れや社内コードの呼び出しに。

[3]

Global StandardvsData ZonevsPTUvsバッチ

Global Standard
既定。最新・最安・地域が最多。
Data Zone
処理を US／EU／APAC 内に限定。
PTU
能力を予約。安定した大量負荷と低い遅延のばらつき。
バッチ
24時間以内目標の一括処理。50%安い。

見分け方条件がなければ Global Standard。「データの所在」→ Data Zone、「安定・大量」→ PTU、「急がない大量」→ バッチ。

プロンプトvsRAGvsファインチューニング

プロンプト
指示や例を工夫する。一番手軽で最初に試す。
RAG
外部の資料を検索して渡す。知識を足し、出典を示す。
ファインチューニング
追加で学習させる。口調・形式・作業のやり方を固定する。

見分け方「社内の最新情報に答えたい」→ RAG。「いつも同じ形式・口調で」→ ファインチューニング。まずはプロンプトから。

[1]

Foundry IQvsメモリvsファイル検索

Foundry IQ
組織で整えた資料に根拠づける。
メモリ
利用者ごとの好みや過去のやり取りを覚える。
ファイル検索
その会話で渡された文書を探す。

見分け方「誰の・いつの情報か」で選びます。会社の資料 → IQ、その人の情報 → メモリ、いま渡された資料 → ファイル検索。

[8][5]

ハイブリッド検索vsセマンティックランカー

ハイブリッド
キーワードとベクターで「探す」（1段目）。RRF でまとめる。
セマンティック
見つかった上位50件を「並べ替える」（2段目）。

見分け方役割が違うので対立しません。「探し方」と「並べ替え」で、併用すると一番よく効きます。

[29][30]

Content UnderstandingvsDocument Intelligence

Content Understanding
生成AIで、非定型の文書や画像・音声・動画まで柔軟に処理。Markdown 出力。
Document Intelligence
定型の書類から、決まった方法で確実に抜き出す。

見分け方「マルチモーダル」「RAG やエージェント向けの整ったテキスト」→ CU。「定型の帳票を確実に」→ DI。

[21][23]

ユーザープロンプト攻撃vsドキュメント攻撃

ユーザー
利用者が入力欄から直接「ルールを無視して」と仕掛ける。既定でオン。
ドキュメント
資料・メール・Web・画像の中に命令を隠す（間接攻撃）。既定でオフ。

見分け方「どこから入ってきた命令か」。外部の資料やツールの応答なら、ドキュメント攻撃の検出を有効にします。

[17]

評価vsトレースvs監視

評価
回答の品質や安全性を「採点」する。
トレース
1回の処理の中身を「追跡」する。
監視
本番の数値を「見張り」、異常でアラートを出す。

見分け方「なぜこの回答になったか調べたい」→ トレース。「品質が落ちていないか」→ 評価と監視。

[14]

根拠性の評価vs根拠性の検出

評価
開発・運用の中で、回答の根拠性を点数にする（エバリュエーター）。
検出
その場で根拠のない回答を見つける安全機能（ガードレール、プレビュー）。

見分け方「テストして測る」→ 評価。「本番の回答をリアルタイムで止める」→ 検出。

[15][16]

関数呼び出しvsMCPvsOpenAPI ツール

関数呼び出し
実際の実行はアプリ側。アプリに組み込んだ処理を呼ぶ。
MCP
共通規格のサーバーにつなぐ。他のエージェントでも使い回せる。
OpenAPI
API の設計書から、Web API をそのままツールにする。

見分け方「既存の Web API と設計書がある」→ OpenAPI。「複数のエージェントで共通のツールを」→ MCP。

[6][7]

エージェントvsワークフロー

エージェント
自由に考えてツールを使う。答えの道筋が決まっていない作業向け。
ワークフロー
手順を先に決めておく。順番や承認をきっちり守らせたい作業向け。

見分け方「手順が決まっている」「複数の部品の実行順を管理したい」→ ワークフロー。

[10]

マネージド IDvsAPI キー

マネージド ID
Azure が管理する社員証。保管不要で、ロールで権限を絞れる。
API キー
合鍵。全権を持ち、ロールの制限が効かない。漏れると危険。
